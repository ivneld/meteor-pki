# 아키텍처 확장 가이드

구조는 필요가 생겼을 때 한 단계씩 키운다. 이 템플릿은 `domain`, `usecase`, `api` 세 계층으로 시작하고, 대부분의 성장은 그 안에서
해결된다. 판단의 기준은 [ARCHITECTURE.md 의 설계 원칙](ARCHITECTURE.md#설계-원칙), 특히 "지금도 이득을 주는 대비만 한다"이다.

## 트리거와 대응

| 트리거 | 하지 말아야 할 것 | 해야 할 것 |
|---|---|---|
| 새 기능·도메인이 생겼다 | 새 애플리케이션이나 모듈부터 만든다 | 같은 계층에 클래스를 추가한다. [ARCHITECTURE.md 의 새 기능 추가](ARCHITECTURE.md#새-기능-추가) |
| `domain` 패키지가 너무 커져 한눈에 들어오지 않는다 | 계층 구조를 버리고 기능별로 다시 짠다 | 계층은 유지한 채 그 안에 도메인별 하위 패키지(`domain.order`, `domain.payment`)를 만든다. 패키지 이동만으로 끝나며 ArchUnit 규칙은 `com.meteor.pki.domain..` 패턴이라 그대로 동작한다 |
| `*Writer` 하나가 비대해졌다 | `*Service`, `*Manager` 같은 새 이름으로 쪼갠다 | 먼저 규칙이 Writer 에 새어 있지 않은지(S-04) 보고 애그리거트·Policy 로 내린다. 그래도 크면 `*Writer` 를 둘로 나누되 이름은 `*Writer` 로 끝낸다 |
| 전체 요청이 늘어 응답이 느리다 | 코드를 나눈다 | 인스턴스를 늘린다. 앱은 무상태이므로 코드 변경이 없다. 먼저 병목이 앱인지 DB인지 외부 API인지 지표로 확인한다 |
| 조회 API 가 무겁다 | 인스턴스를 늘린다 | 조회 전용 `*Reader` 메서드와 Spring Data 쿼리로 필요한 컬럼만 읽고 캐시한다. 여러 테이블을 묶는 화면은 조회 전용 `*Reader` 에서 JOIN 쿼리로 만든다 |
| 외부 API 호출이 느려 DB 커넥션이 마른다 | 커넥션 풀만 늘린다 | 그 유스케이스를 `TransactionTemplate` 으로 나눠 외부 호출을 트랜잭션 밖으로 뺀다. [ARCHITECTURE.md 트랜잭션 나누기](ARCHITECTURE.md#나누기) |
| 같은 저장소에 배치·어드민 같은 두 번째 실행 모듈이 필요하다 | 도메인 규칙을 새 모듈에 복사한다 | [core-domain 모듈 추출](#core-domain-모듈-추출) |
| 새 애플리케이션이 이 애플리케이션의 데이터·규칙을 필요로 한다 | 새 앱이 이 앱의 DB 를 직접 읽는다. 새 앱에 규칙을 다시 구현한다 | [다른 애플리케이션과 연동하기](#다른-애플리케이션과-연동하기) |
| 팀이 나뉘어 배포를 서로 기다린다 | 코드만 나눈다 | 서비스 분리를 검토한다. 그 전에 도메인 사이 결합을 줄인다. [서비스를 나눠야 할 때](#서비스를-나눠야-할-때) |
| 멀티테넌트 서비스다 | 나중에 넣는다 | **첫날에 결정한다.** 격리 방식(스키마/컬럼), 모든 쿼리의 테넌트 조건 강제, 테넌트 단위 감사. 컬럼 방식이면 Hibernate `@TenantId` 가 조건 누락을 구조적으로 막는다 ([ARCHITECTURE.md 영속화 결정](ARCHITECTURE.md#영속화-결정)) |

트래픽, 코드 크기, 도메인 개수는 서비스 분리의 이유가 아니다. 각각 수평 확장, 패키지 정리, 모듈 추출로 해결되며 전부 하나의 배포 단위
안에서 가능하다. 분리의 이유는 **조직(독립 배포)** 과 **데이터(저장소 격리)**, **운영 등급** 에서만 나온다.

## 확장 프로세스

1. **측정한다.** 병목이 앱 스레드인지, DB 커넥션인지, 외부 API 인지 지표로 확인한다. `support/monitoring` 이 이 단계에 쓰인다.
2. **가장 싼 수단부터 쓴다.** 인스턴스 추가 → 조회 최적화·캐시 → 트랜잭션 분리 → 실행 모듈 추가(DB 공유) → 서비스 분리(DB 분리).
   각 단계는 앞 단계로 해결되지 않는다는 근거가 있을 때만 간다.
3. **규칙은 처음부터 지킨다.** 구조를 바꾸는 비용은 그동안 규칙에 낸 예외의 개수로 결정된다. 예외는 [ARCHITECTURE.md](ARCHITECTURE.md) 의
   절차대로 동결하고 ADR 로 남긴다.
4. **다시 측정한다.** 바꾼 구조가 해결하려던 지표가 실제로 바뀌었는지 본다.

## core-domain 모듈 추출

배치처럼 같은 도메인 규칙을 쓰는 두 번째 실행 모듈이 생기면 `com.meteor.pki.domain` 과 `com.meteor.pki.support.error` 를 라이브러리 모듈
`core/core-domain` 으로 옮긴다. core-enum 과 storage 는 이미 모듈이다.

```
core-api   ──┐
             ├──► core-domain ──► storage/db-core ──► core-enum
core-batch ──┘
```

- 저장소 어댑터(`*Repository`)가 domain 에 있으므로 엔티티 ↔ 애그리거트 변환도 함께 옮겨진다. 실행 모듈마다 변환 코드를 다시 쓰지 않는다.
- 도메인 모델은 R-01 로 프레임워크를 모르고, domain 은 usecase·api·client 를 모르므로 파일 이동으로 끝난다.
- usecase 는 애플리케이션마다 다르므로 옮기지 않는다. 배치는 자기 모듈에 흐름과 트랜잭션 경계(예: 청크 단위 커밋)를 둔다. 도메인 서비스는
  기본 전파라 배치의 청크 트랜잭션에 그대로 참여한다.
- `ArchitectureRules` 는 core-domain 이 아니라 각 실행 모듈의 테스트에 두고 `com.meteor.pki` 전체를 검사한다.

## 다른 애플리케이션과 연동하기

새 애플리케이션이 이 애플리케이션의 데이터나 규칙을 필요로 할 때.

1. **DB 를 공유하지 않는다.** 새 앱이 이 앱의 테이블을 직접 읽는 순간 그 스키마는 두 앱의 계약이 되어 바꿀 수 없다. 읽기 전용이라도
   마찬가지다.
2. **규칙은 API 로 연다.** 판단은 이 앱의 애그리거트가 하고 결과만 돌려주는 내부 API 를 만든다. 새 앱에 규칙을 다시 구현하지 않는다.
   예: `MemberReader.ensureActive()` → `GET /internal/members/{id}/active`.
3. **변경 통지가 필요하면 그 경계에만 메시지를 둔다.** 새 앱이 알아야 하는 변경만 발행하고, 유실을 막는 장치(Outbox 등)도 이 시점에 이
   경계에만 둔다.

## 서비스를 나눠야 할 때

조직·데이터·운영 등급 기준이 생겨 일부 도메인을 별도 서비스로 옮겨야 한다면, 그 전에 같은 애플리케이션 안에서 결합을 줄인다.

- [ ] 옮길 도메인의 클래스를 계층마다 하위 패키지(`domain.payment`, `usecase.payment`)로 모은다.
- [ ] 옮길 도메인과 남을 도메인을 함께 엮는 usecase 를 찾는다. 이 목록이 서비스 간 호출이나 메시지로 바꿀 대상이자 비용의 추정치다.
- [ ] 그 usecase 가 한 트랜잭션으로 묶고 있다면 나눌 수 있는지, 나누면 중간 상태와 재실행을 어떻게 다룰지 정한다([트랜잭션 나누기](ARCHITECTURE.md#나누기)).
- [ ] 옮길 도메인의 테이블을 다른 도메인이 JOIN 하는 쿼리를 없앤다.
- [ ] 테이블을 별도 DB 로 옮기는 것까지 끝낸다. DB 를 공유한 채 멈추면 분산 모놀리스가 되어 양쪽의 단점만 남는다.

## 처음부터 하지 않는 것

과도한 대비를 막는 선이다.

- 도메인별 패키지·모듈로 미리 쪼개지 않는다. 세 계층으로 시작한다.
- 도메인 사이에 Facade, 이벤트 같은 통로를 미리 두지 않는다. 여러 도메인을 엮는 일은 usecase 가 한다.
- 메시지 브로커, Outbox, 이벤트 저장소를 두지 않는다. 다른 애플리케이션과 연동하는 경계가 생길 때 그 경계에만 둔다.
- 저장소 교체를 위한 인터페이스를 두지 않는다. 영속화는 JPA 로 고정이다.
- 서비스 간 HTTP, 사가, 분산 추적 인프라를 두지 않는다.
